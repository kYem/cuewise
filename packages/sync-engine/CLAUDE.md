# CLAUDE.md - Sync Engine (packages/sync-engine)

AI-assistant guide for `@cuewise/sync-engine`. Read the root [`CLAUDE.md`](../../CLAUDE.md) first — this file only covers what's specific to this package.

## What This Is

The ENG-45 orchestration layer sitting above `@cuewise/sync-client` (the wire — HTTP transport, retries, session) and `@cuewise/crypto` (the cipher — record sealing, key management). This package owns the logic neither of those leaves handles: mapping domain entities (goals, quotes, ...) to push/pull records, conflict resolution, and the fresh-device migration/merge state machine.

## Design Rules

- **Conflict resolution behind `ConflictStrategy`.** Never inline last-write-wins (or any other policy) at a call site — express it as a swappable strategy so the policy can change without touching orchestration code.
- **All sync metadata lives in `SyncMetadataStore`, never on domain types.** Goals/quotes/etc. in `@cuewise/shared` stay platform- and sync-agnostic; version vectors, last-synced timestamps, and dirty flags belong to this package's own store, not bolted onto shared entities.
- **Change the ledger through `SyncMetadataStore.update`, never `load` → mutate → `save`.** The ledger is one blob, so a `save` of a snapshot taken before a network round trip erases every edit marked dirty during it — and with push-on-change that overlap is routine, not rare. `update` serialises load → mutate → save on a promise chain, and a caller that spans a round trip (`pullOnce`, `pushOnce`) must pass a **delta** to it — what that cycle itself owns — rather than the snapshot it has been holding. A delta may claim a per-entity field only while the stored ledger has not stamped that key past it meanwhile (`mergePull`'s hlc guard, `clearAcked`'s): a cycle is always the older news when it loses that race. `load`/`save` remain for reads and for `update`'s own use. **That chain is per `SyncMetadataStore` instance, so it assumes exactly one `SyncEngine` per `KeyValueStore`** — true today (the extension's page realm forwards over `chrome.runtime` rather than holding an engine of its own), and silently void the moment a second engine is constructed against the same store.
- **Platform-agnostic via ports.** Like `@cuewise/sync-client`, this package consumes only `@cuewise/shared/platform` ports (`KeyValueStore`, `Scheduler`) — no `chrome.*`, no DOM, no Tauri imports — so the browser extension and the Tauri macOS app share one implementation.

## What's Here

`collections.ts` (entity ↔ record bindings), `strategy.ts` (`ConflictStrategy` / `LwwHlcStrategy`), `metadata-store.ts` (`SyncMetadataStore`), `mutation-tracker.ts` (`markMutated`/`markDeleted` → dirty-set + HLC), `record-map.ts` (seal/open a `PushRecord`), `key-lifecycle.ts` (enroll/self-heal), `cycle.ts` (`pullOnce`/`pushOnce`), `engine.ts` (`SyncEngine`, the public façade tying all of it together), and `create-engine.ts` (`createSyncEngine`, the one-call host constructor). `golden-path.test.ts` is the two-device end-to-end integration test (two `SyncEngine`s, separate `FakeKvStore`s, one shared `FakeSyncServer`) plus the swappability guard (`__fixtures__/noop-strategy.ts`'s `NoopStrategy`, which always returns `{winner:'local'}` — proves `SyncEngine`/`cycle.ts` route every conflict decision through `ConflictStrategy` and hardcode no LWW).

## `createSyncEngine` (`create-engine.ts`)

Host apps should construct through this factory rather than hand-assembling `ApiClient` + `SessionManager` + `SyncEngine`: `createSyncEngine({ baseUrl, keyStore, scheduler, ...SyncEngineDeps overrides })` builds a `SessionManager` over `keyStore`, an `ApiClient` wired to that session's `getToken`, constructs the `SyncEngine`, and — as its last step — calls `configurePlatform({ syncSink: engine })` (from `@cuewise/shared/platform`) so the engine is immediately wired as the store layer's `SyncMutationSink`. Constructing the engine IS registering it; there's no separate manual step, so it can't be forgotten. (`SyncEngine` itself does not self-register in its constructor — only this factory does — so `engine.test.ts`/`golden-path.test.ts`, which build `SyncEngine` directly with fakes, never touch global platform state.) This is what both `apps/browser-extension/src/background.ts` and `apps/macos/src/main.tsx` call.

**A non-empty `VITE_SYNC_API_BASE_URL` IS the enable signal** — when set it also enables the Cloud Sync settings section. Release builds ship with it set (`release.yml` passes `vars.VITE_SYNC_API_BASE_URL`), so **cloud sync is enabled in production**; a local build without the var has sync off and never constructs the engine. When it's set, both hosts call `engine.start()` unconditionally (a no-op unless `enableSync()` was already run some other way, e.g. devtools) and wire the pull-wake wire below. Production reaches the API through the `https://*.cuewise.app` entry already in `connect-src`; the extension's `manifest.config.ts` and the Tauri app's `tauri.conf.json` `devCsp` (never `csp`, the production block) additionally allow the *local wrangler* sync origin in non-production builds only.

## `SyncEngine` (`engine.ts`)

The one class apps construct. Public surface: `enableSync(provider, credential, deviceName, {recoveryCode?, codeVerifier?})`, `resumeEnrollWithCode(recoveryCode)` (ENG-65: finishes a needs-code enroll against the still-live session, so device #2 supplies the code without a second sign-in bounce; no-ops to `signed_out` if that session was lost), `disableSync()`, `syncNow()` (pull-then-push), `start()`/`stop()` (arms/cancels the periodic pull wake), `markMutated`/`markDeleted` (delegate to `MutationTracker`), `getStatus()`. Status walks `disabled → signing_in → key_init/enrolling → initial_sync → active`, or `needs_enroll`/`signed_out`/`error` on failure; every transition calls `deps.onStatus?.(status)`.

**A disable cancels the cycle in flight.** `disableSync()` bumps an account epoch, and `runCycle` hands the cycle an `isCancelled` closure over it (`CycleDeps.isCancelled`, required so a caller cannot silently opt out). Once it answers true the cycle stops without writing or saving anything further: no further record is applied, and **no ledger write runs on either side** — including `pushOnce`'s write after a batch acks, which would land on whatever ledger is enrolled by then rather than the one that sealed the batch. That last one is belt-and-braces: `clearAcked` only clears an id whose ledger hlc still matches what the batch sealed, so it already no-ops against a reset or re-enrolled ledger. Losing that ack costs one re-push the next enable makes anyway. Both ledger writes are enqueued **synchronously** after their cancel check — `SyncMetadataStore.update` queues on the chain before it awaits anything — and an `await` introduced between the two would let a disable reset the ledger first and have the stale delta restore what it cleared.

`enrollAndActivate` takes its caller's epoch — snapshotted before sign-in, since a disable landing during the token exchange would move it before a later snapshot could read it — and checks it at four points: after the key is minted, after the backfill, after the cycle, and after `cloudSyncEnabled` is written. A superseded enroll rolls back everything it wrote — the data key, the session, the ledger and the enabled flag — and names any it could not remove, since `remove` reports failure by returning `false` rather than throwing. The session matters because `disableSync` clears it before this enroll's `saveToken` writes it, and a live token keeps `getAccount` naming the disconnected account; the key because left on disk it would seal the NEXT account's records under a key whose server holds no envelope, making that device's records unreadable everywhere else. What it cannot roll back is the recovery envelope (there is no delete call), so a code it minted is logged AND handed to the host, which surfaces it — that account outlives the attempt and nothing else can re-enroll it. `enrollSuperseded` writes `disabled` itself rather than leaving it to the disable, which sets it last, after several awaited storage hops: both hosts read the post-enable status to decide whether the connect worked, and would otherwise see a mid-enable one and report success. `enrollAndActivate` also resets the pull cursor **unconditionally** before the initial sync. The enabled flag cannot stand in for "this cursor is mine": it is only written once an enable finishes, and it survives `handleAuthLoss`, so a reconnect that lands on a different account at the provider's chooser would inherit the previous account's high-water mark.

`syncNow()` answers `SyncNowResult`, which is `SyncOutcome` plus `{kind:'cancelled'}`; keeping `cancelled` outside `SyncOutcome` is what makes the compiler refuse to record, persist or paint it as a cycle that ran. Both hosts treat a post-enable status of `disabled` as an abandoned enable and answer `reason:'cancelled'`, carrying any code it minted — otherwise `ok:true` persists creds for a removed account and hands Chrome sync off. The panel gives that its own route: it closes the enable form, surfaces the code and explains it. Only a cancelled SIGN-IN is quiet.

`SyncEngineDeps.apiClient` is typed as `EngineApiClient` — a `Pick<ApiClient, ...>` structural subset (auth + pull/push + key-envelope calls), not the concrete `ApiClient` class. A real `ApiClient` instance satisfies it directly (structural typing); tests substitute an in-memory fake. `sessionManager`/`keyStore`/`scheduler` take the real `SessionManager` class / `KeyValueStore` / `Scheduler` ports directly — construct `SessionManager` over a fake `KeyValueStore` in tests instead of hand-rolling a fake session manager.

**Host wiring — the pull loop.** `armSyncPull` (from `@cuewise/sync-client`) only schedules a *single* wake; something has to re-arm it forever. `SyncEngine` does not hold a live `SchedulerHost` subscription itself (only the command-only `Scheduler` port), so the resident host (extension service worker, Tauri app loop) is responsible for the fire subscription:

```typescript
schedulerHost.onFire((id) => {
  if (id === SYNC_PULL_WAKE_ID) {
    engine.handlePullWake(); // runs syncNow() then re-arms the next wake
  }
});
```

`engine.start()` (call once per app/tab open) self-heals the DK against the server, then syncs and arms the first pull wake if `cloudSyncEnabled` is set. The two typed self-heal errors land differently, and the difference is the user-facing one: `SelfHealNeedsEnrollError` (key gone, envelope on the server) is the ordinary lost-key case and lands `needs_enroll`, so the UI asks for the recovery code; `SelfHealUnrecoverableError` (key present, envelope gone) logs at error and **falls through** so the device still syncs — only `regenerateRecoveryCode()` can rebuild the envelope, and it is reachable only from the active panel. A device that reaches `needs_enroll` also stops re-arming the pull wake, since none of its cycles can complete. `engine.stop()` just cancels the armed wake; it does not touch the session or the DK — use `disableSync()` for that.

**Chrome extension realms.** `createSyncEngine` (and thus its own sink registration) only runs in `background.ts`'s service-worker realm, while store mutations happen in `main.tsx`'s page realm — separate MV3 JS module state, so the engine's sink is not reachable from the page. The page realm registers its own sink instead: `main.tsx` calls `configurePlatform({ syncSink: new ChromeRuntimeSyncSink() })`, which forwards `markMutated`/`markDeleted`/`markMutatedBulk` to the worker over `chrome.runtime` messaging. Page-realm mutations therefore do push. The macOS app is unaffected (single Tauri webview realm).

**Settings are per-key, not a blob.** `settingsBinding.writeOne` and the page realm's `settings-store` each persist only the key(s) they touch, so two writers on *different* keys in different realms can no longer clobber each other. Two writers on the *same* key still resolve last-write-wins via `ConflictStrategy` — that's the intended sync semantics, not a bug. A realm's in-memory settings snapshot no longer goes stale after a pull it didn't perform itself: `KeyValueStore.onChanged` (optional, feature-detected) reports which keys changed, and `settings-store` re-reads on any of its own. `ChromeKeyValueStore` implements it over `chrome.storage.onChanged`, which is what crosses the worker/page boundary; `LocalStorageKeyValueStore` emits its own writes, since the single-document hosts on that backend get no `window.onstorage` for themselves.

**Auth loss.** Any 401 (during `enableSync`, `syncNow`, or the pull wake) clears the session and stops the loop but keeps local data *and* the DK — status goes to `signed_out` so the user can silently re-authenticate later without re-enrolling the key. That is exactly what distinguishes it from `needs_enroll`, where the key is what is missing and no amount of re-authenticating helps. A 401 that a disable provoked is not auth loss at all — the epoch checks answer it first, so the user's own disconnect is never reported as an expired sign-in.
